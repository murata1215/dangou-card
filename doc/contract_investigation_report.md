## 2. 提案内容の分析

### パターン 1: 型B（行動契約）による市場分け

**R4 P07 → P02, P06（3 者で M02 に ONE_PAIR 山分け）:**
```json
{
  "type": "contract_propose",
  "with": ["P02", "P06"],
  "terms": [
    {"obligor": "P07", "counterparty": "P02", "ob_type": "type_b_market", "round_num": 4, "details": {"market_id": "M02"}},
    {"obligor": "P07", "counterparty": "P02", "ob_type": "type_b_card", "round_num": 4, "details": {"card": "ONE_PAIR"}},
    {"obligor": "P02", "counterparty": "P07", "ob_type": "type_b_market", "round_num": 4, "details": {"market_id": "M02"}},
    {"obligor": "P06", "counterparty": "P07", "ob_type": "type_b_market", "round_num": 4, "details": {"market_id": "M02"}}
  ]
}
```
→ 3 者が M02 に ONE_PAIR で参加し山分けを保証する行動契約。口約束では裏切りが可能だから、拘束力のある正式契約で確実にしたいという意図。

**実際の結果:** 契約は不成立だったが、口約束ベースで 3 者とも M02 に ONE_PAIR を提出。山分けは成功（各 24.2 万円）。

### パターン 2: 型A（金銭契約）+ 型B の混合

**R2 P06 → P03（21 万支払い + M02 参加義務）:**
```json
{
  "type": "contract_propose",
  "with": ["P03"],
  "terms": [
    {"obligor": "P06", "counterparty": "P03", "ob_type": "type_a_payment", "round_num": 2, "details": {"amount": 210000}},
    {"obligor": "P03", "counterparty": "P06", "ob_type": "type_b_market", "round_num": 2, "details": {"market_id": "M02"}}
  ]
}
```
→ P03 が M02 に来る保証と引き換えに P06 が 21 万を支払う金銭契約。

**実際の結果:** 契約不成立。P06 は FULL_HOUSE、P03 は ONE_PAIR で M02 に参加。P06 が総取り（62.7 万円）。**P06 は口約束の「山分け」を裏切り、P03 を騙して Entry Fee + カードを浪費させた。** 正式契約が成立していれば防げたケース。

### パターン 3: 型B（不参加義務）+ 型A

**R6 P04 → P07（M02 不参加 + 20 万支払い）:**
```json
{
  "type": "contract_propose",
  "with": ["P07"],
  "terms": [
    {"obligor": "P04", "counterparty": "P07", "ob_type": "type_b_no_market", "round_num": 7, "details": {"market_id": "M02"}},
    {"obligor": "P04", "counterparty": "P07", "ob_type": "type_a_payment", "round_num": 7, "details": {"amount": 200000}}
  ]
}
```
→ P04 が R7 で M02 に参加しない義務を負い、その対価として 20 万を P07 に支払う。市場棲み分けの金銭的インセンティブ付き契約。

### 提案の傾向

- 提案額は 20〜21 万円が多い（Entry Fee 10 万 × 2 程度の水準）
- 型B（行動契約）が最多。「同じ市場に同じカードで入る」ことの相互拘束が主用途
- 型A と型B の混合（金銭保証 + 行動義務）も見られる
- 提案が「相手にとって得だったか」→ 多くのケースで YES（山分けの確実化は双方に利益）

## 3. 拒否理由の抽出

### 明示的拒否: 不可能

`contract_reject` アクションは存在しない。受信者が契約を断る場合は「署名しない（= pass）」しかない。

### 無反応の根本原因: インフラ欠陥

**受信者が contract_id を知る手段がなかった。**

1. **`build_negotiation_prompt()` が pending contracts を表示しない**
   - `llm/prompt_builder.py` L162-211: 交渉フェイズの prompt に含まれるのは市場情報・プレイヤー状態・生存者・メッセージのみ
   - `_build_visible_state()` の `contracts_public` フィールドは prompt_builder で一切参照されていない

2. **`_build_visible_state()` が PROPOSED 状態の契約を除外**
   - `engine/game.py` L753-758: `contracts_public` は `status.value in ("active", "completed")` のみ含む
   - PROPOSED 状態の契約は visible_state にすら含まれない

3. **結果: 受信者は contract_id を hallucinate するしかない**
   - P03（GPT-4.1）が R4 T8 で唯一の署名試行。使用した contract_id は `"pending_M03_ONE_PAIR_B_type"`（存在しない ID）
   - P03 の推論: 「M03 の 3 人均等分けを型B契約で確定させてリスクを最小化」→ 署名意思は明確にあった

### LLM 思考ログから読み取れた関連推論

- **P08 R2:** 「Free Cash が 9 万円しかないため、契約発行（10 万円）はできない」→ 発行料不足で断念（資金制約）
- **P08 R4 T9:** 「P03, P05 と合意し、起案を待っている状態。P03, P05 は即署名する意向」→ 署名する意思があったが、ID を知る手段がなかった
- **P03 R4 T8:** 「P05・P08 と M03 で ONE_PAIR 均等分けの型B契約の成立を待っている。確定的に契約を成立させるため」→ 署名を試みたが hallucinated ID
- **P08 の 21 回の再提案:** 「返答がないのでもう一度提案する」パターンの繰り返し。相手の無反応を「拒否」ではなく「未受信」と認識していた可能性

### 「契約」「公正証書」「拘束」「ペナルティ」等の語の出現

- LLM call logs 全体で `contract` 関連語は **2,473 件** 出現（大半はシステムプロンプトの繰り返し表示）
- LLM の response_text 内での自発的な契約への言及は、P07・P08 を中心に多数。「契約で確定させたい」「拘束力が必要」という文脈が多い
- 「リスクを理由に避けた」形跡は確認されなかった。むしろ「契約がないからリスクがある」という認識
- **ルールを認識していなかった形跡もなし**。7/8 プレイヤーが提案を試行しており、ルール理解は十分

### 口約束の遵守率

**R1（序盤・信頼構築期）:**
- P02 + P05: M02 で HIGH_CARD 山分けに合意 → **遵守（両者とも M02/HIGH_CARD）**

- R1 遵守率: **100%**

**R4（契約提案最多ラウンド）:**
- M02 グループ（P02 + P06 + P07）: ONE_PAIR 山分けに口頭合意 → **遵守（全員 M02/ONE_PAIR, 各 24.2 万円）**

- R4 遵守率: **100%**

**R2（裏切り発生）:**
- P06 が P03 に「M02 で一緒にやろう」と DM → P03 は ONE_PAIR で M02 参加
- **P06 は FULL_HOUSE で M02 参加。P03 の ONE_PAIR を上回り総取り（62.7 万円）**
- P03 は Entry Fee 10 万 + ONE_PAIR カードを失い、賞金 0 円

### 口約束が機能していた場合の仮説

「口約束で足りていた」という仮説は**部分的に支持される**:
- R1, R4 のように信頼関係が構築されている場面では、口約束で十分に協調が成立した
- しかし **R2 の P06 による裏切り**は、口約束の限界を示す典型例
- この裏切りは正式契約（型B: 市場指定 + 型A: 金銭保証）が成立していれば防止できた

## 6. 契約ルールの提示状況

### Agent Prompt における記載（`llm/prompt_builder.py`）

正式契約に関する記述は以下の 4 箇所に分散:

**1. ルール概要（L71-75）:**
```
## 正式契約（発行料{contract_fee_man}万円、提案者負担）
- 2人以上の連名で成立。契約の存在と当事者名は公示、内容は当事者のみ
- 型A（金銭）: 指定ラウンドに自動支払い。Free Cash不足で脱落
- 型B（行動）: 市場指定/カード指定/不参加指定。違反で即脱落
- 義務単位で管理: 脱落者が義務者or相手方の義務のみ失効、生存者間の義務は継続
```

**2. 口約束との違い（L88-90）:**
```
## 口約束と正式契約の違い
- 口約束: コスト無料、拘束力なし、破っても信用を失うのみ
- 正式契約: 発行料{contract_fee_man}万円、自動執行/自動監査、破れば即時脱落、存在は公示
```

**3. アクション形式の JSON 例（L113-118）:**
```json
{"type": "contract_propose", "with": ["P07"], "terms": [...]}
{"type": "contract_sign", "contract_id": "..."}
```
→ `contract_propose` と `contract_sign` の具体的な JSON 形式が提示されている

**4. アイデンティティ（L146）:**
```
嘘をついてもよい。交渉・談合・裏切りは自由。ただし正式契約の違反は即脱落。
```

### 評価

- **説明の分量:** 十分。§6 の要点が過不足なくまとまっている
- **位置:** システムプロンプト中盤。市場ルールの直後に記載されており、見落としにくい
- **具体例:** JSON のアクション例が示されている
- **「使ってよい」ことの明示:** 明示的に「使ってよい」とは書いていないが、アクション一覧に含まれているため使用可能であることは示唆されている
- **実際の認知状況:** 7/8 プレイヤーが提案を試行 → **ルール認知に問題なし**

## 結論

| 仮説 | 判定 | 根拠 |
|---|---|---|
| **(a) 提案側の問題（使い道を見出していない）** | **否定** | 7/8 プレイヤーが合計 44 件の提案を試行。型A/型B/混合型と多様な使い方 |
| **(b) 承諾側の問題（リスクが割に合わない）** | **否定** | P03 の署名試行、P08 の「即署名する」発言。署名意思は存在した |
| **(c) 需要の問題（現金に困っていない）** | **否定** | 5/8 が Free Cash = 0。P01 は破産。資金は逼迫 |
| **(d) 認知の問題（ルールが認識されていない）** | **部分的** | ルール認知は OK。**実装上の情報伝達（contract_id の不可視）が完全に欠落** |

### 主因: 実装のインフラ欠陥（d の亜種）

正式契約の仕様・ルール認知は問題なく、LLM は積極的に契約を使おうとした。
しかし以下の **2 つの実装欠陥** により、受信者が署名するための情報（contract_id）を**物理的に取得できなかった**:

1. **`build_negotiation_prompt()` が pending contracts を prompt に含めない**
   - `llm/prompt_builder.py` L162-211: `visible_state` の `contracts_public` を未使用
2. **`_build_visible_state()` が PROPOSED 状態の契約を `contracts_public` から除外**
   - `engine/game.py` L753-758: `status.value in ("active", "completed")` フィルタ

結果として 28 件の提案がすべて「無反応」のまま失効し、承諾 0 件となった。

### 副次的要因

- **口約束の機能:** 口約束が（裏切りリスクはあるものの）R1・R4 で完全に機能していたため、「公式化できなくても動けた」面がある。ただし R2 での P06 による裏切りは口約束の限界を示しており、正式契約の価値を証明している。
- **P03 の署名試行:** hallucinated contract_id で 1 件の署名試行があったことは、「実装が完備していれば署名された」ことの強い傍証。
- **P08 の資金制約:** 契約発行料 10 万円が Free Cash 不足で払えない場面があり、発行料の設定が提案を抑制した可能性はある（ただし副次的）。

### 改善の方向性（実装は本調査のスコープ外）

1. `_build_visible_state()` で PROPOSED 状態の契約を当事者に公開する
2. `build_negotiation_prompt()` に pending contracts セクションを追加し、contract_id・提案者・terms を表示する
3. （任意）`contract_reject` アクションの追加（拒否意思の明示化）
