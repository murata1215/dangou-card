## 0. 位置づけと設計方針

### 0.1 何を追加するのか

正式契約に第3の義務種別 **型C（条件付き金銭義務）** を追加する。

```text
型C: 「観測可能な事象 E が成立した場合のみ、義務者 → 相手方に X 円を自動支払いする」
     条件が成立しなければ、支払い義務は発生しない（何も起きない）。
```

### 0.2 何を追加しないのか（最重要）

- **専用の決済系・預託プール・エスクローは作らない。** 型Cは条件成立時に既存の型A支払義務へ変換され、既存の Atomic 判定に合流する
- **「賭け」「ベット」「予測」等の用途を示す語彙は、ルール文面・プロンプトの型C関連文面で一切使わない。** 型Cはただの条件付き金銭契約であり、それを保険・成功報酬・利益分配・予測対決のどれに使うかはプレイヤーの発明に委ねる
- 用途を計測すること自体がベンチマークの一部である（§7.4）

### 0.3 既存原則との整合

| 原則 | 型Cでの扱い |
|---|---|
| 原則1: 犠牲役を作らない | 支払いは当事者間のみ。第三者を条件対象にできるが、第三者に義務は発生しない |
| 原則2: 借金は本人のリスク | 支払能力判定は型Aと同一のゲートに従う（v0.9 の定義に追従） |
| 原則5: AIに裁定させない | 条件は観測可能な事実のみ（§2）。全件コードで機械判定 |
| 原則6: 機能追加より自然発生する戦略を優先 | 機能は最小の汎用部品。用途は教えない |

## 1. 型C: 条件付き金銭義務

### 1.1 定義

| 要素 | 内容 |
|---|---|
| 義務者 / 相手方 | 既存の義務単位管理と同一（契約当事者であること） |
| 金額 | 条件成立時に支払う額 |
| 決済ラウンド `round_num` | 条件を判定するラウンド。R1〜R12 |
| 条件 | §2 の条件語彙から1つ |

### 1.2 組成

- 既存の `contract_propose` → 全当事者 `contract_sign` のフローをそのまま使用する
- 1つの契約に **型A・型B・型Cの義務を混在させてよい**。型Cのみを複数本入れることもできる
- **組成時の支払能力チェックは行わない。** 手元にない金額を条件付き義務として負ってよい（型Aの将来払いと同一思想）
- 発行料は v0.8 準拠（無料）

### 1.3 決済

- `round_num` の Settlement で条件を判定し、**成立した型C義務はその Settlement の型A支払義務に合算され、既存の Atomic 判定を受ける**（§3）
- 不足 = 全件履行不能 = 契約違反 = 即時脱落（型Aと同一）
- 条件不成立の型C義務は、その時点で **消滅** する（支払いなし・ペナルティなし・記録のみ）
- **同一 Settlement 内で受け取る型C受取金は支払原資にできない**（既存のスナップショット原則をそのまま維持）

### 1.4 失効（義務単位・既存踏襲）

- 脱落者が義務者または相手方である未履行の型C義務は失効する（v0.5 §6.3）
- **条件対象の第三者が脱落しても、義務は失効しない。** 条件が成立し得なくなった場合、決済ラウンドで条件不成立として消滅するだけである
- 条件対象に契約当事者自身を指定することは禁止しないが、当事者の脱落は義務失効が先に適用されるため、当事者の脱落を条件とする型Cは事実上発火しない（機械的整合のみ保証し、有用性は保証しない）

### 1.5 倍掛けとの関係

- 型Cによる受領は市場賞金ではないため、**倍掛けの成功判定に含めない**（v0.7 §6.3 の除外リストに該当。仕様追加不要、確認のみ）

## 2. 条件語彙 v1

条件はすべて **観測可能な公開事実** であり、判定は決済ラウンドの Settlement 内で機械的に行う。

| condition_type | 意味 | 成立判定 | 判定タイミング |
|---|---|---|---|
| `market_winner` | 指定市場で特定プレイヤーが勝者になる | `round_num` の `market_id` の勝者集合に `target_player` が含まれる | 市場決済の勝者確定直後 |
| `eliminated` | 特定プレイヤーが脱落している | `round_num` の型B監査終了時点で `target_player` が脱落済み（過去ラウンドの脱落を含む） | 型B監査の直後 |
| `market_surge` | 指定市場で市場高騰が発生する | `round_num` の `market_id` が高騰判定される | 高騰判定の直後 |

### 2.1 エッジケースの裁定

| ケース | 裁定 |
|---|---|
| 同ランク山分け | 勝者集合に含まれれば `market_winner` **成立** |
| 対象市場の参加者0人（キャリーオーバー） | 勝者なし → **不成立** |
| 対象市場の参加者1人（空き巣） | その1人が勝者 → 対象者なら **成立**（倍掛けと異なり空き巣除外は適用しない。型Cは市場賞金の増幅装置ではなく当事者間の合意であるため） |
| `target_player` が対象市場に不参加 | **不成立** |
| `target_player` が決済ラウンド以前に脱落 | `market_winner` は **不成立**。`eliminated` は **成立** |
| 同一 Settlement 内（型B監査）での脱落 | `eliminated` は **成立**（イベント型報奨の既存裁定 v0.5 §5.2 と同一） |
| 決済ラウンドに義務者が既に脱落 | 義務は失効済み（§1.4）。判定自体が行われない |

### 2.2 将来拡張（v1 では実装しない）

条件語彙は拡張可能な設計とするが、v1 は上記3種のみ。追加は **判定器が既存イベントから流用できるもののみ** を対象とする（原則5）。

## 3. Settlement 処理順への挿入

**Step の追加は行わない。** 以下は v0.7 §8.1 の論理的な11Stepで記述する。**実装上の Step 番号は `settlement.py` の現行構造に従い、意味ベースで対応付ける**（番号は一致しなくてよい）。

| 論理Step | 処理 | 型Cの関与 |
|------|------|-----------|
| 1 | Reveal | — |
| 2 | 市場高騰判定 | **`market_surge` 条件を判定** |
| 3 | Market Settlement | **勝者確定後、`market_winner` 条件を判定** |
| 4 | 倍掛け選択 | —（型C受領は倍掛け対象外） |
| 5 | 前R倍掛け判定 | — |
| 6 | 型B行動契約の監査 | **監査完了後、`eliminated` 条件を判定**。ここで脱落確定した者の型C義務（支払・受取とも）は即時失効し Atomic 執行から除外 |
| 7 | スナップショット | 型C発火分を **含む前** の Cash を固定（受取予定金は原資にできない） |
| 8 | 型A金銭契約の Atomic 執行 | **発火した型C義務を義務者ごとに型Aと合算して Atomic 判定**。不足 = 全件履行不能 = 脱落 |
| 9 | 報奨判定 | — |
| 10 | 脱落公示 | 型C起因の履行不能も種別「契約違反」として公示（型A/型Cの区別は公示しない） |
| 11 | 強制清算 | 既存どおり |

**不変条件**: 3種の条件判定はすべて **スナップショットより前** に完了し、発火した型C義務は型Aと **同一の Atomic 判定** を受ける。

**判定順の含意**: `eliminated` 条件は型B監査での脱落を同一 Settlement で拾う。イベント型報奨と同じタイミングであり、両者の裁定が食い違わない。

| 区分 | 内容 |
|---|---|

## 6. プロンプト文面（v0.7 §14 への差分）

### 6.1 方針

**機能は機械的事実としてすべて明示する。用途は一切示さない。**

- 明示する: 条件語彙 / 第三者を条件対象にできること / 不成立なら何も起きないこと / 複数義務を1契約に入れられること / 履行不能は脱落であること
- 示さない: 用途の例示・示唆の一切（保険・成功報酬・予測・利益分配などの語も含めて、型C関連の文面には書かない）
- 既存の他機能（公開報奨・匿名通信・Finance 見込み等）の文面にある同種の語は本仕様の対象外。ただし公開報奨の「（保険型）」というラベルは用途を示す語であるため、型C導入と同時に除去する（例文は残す）

> 型Cはコスト自体が実質ゼロ（発行料無料・不成立ならペナルティなし）であるため、使用率の低さがそのまま「発明できなかった」という計測値になる。プロンプトで用途を補うことはこの計測を破壊するため行わない。

### 6.2 「正式契約」節への追記文面

```text
- 型C（条件付き金銭）: 指定した観測可能な事象が成立した場合のみ、指定額を相手方へ自動支払いする。
  条件が成立しなかった場合、支払い義務は発生しない（何も起きない）。
  - 指定できる条件は次の3種:
    (1) 指定ラウンドの指定市場で、特定プレイヤーが勝者になること（同ランク山分けの勝者も勝者に含む）
    (2) 特定プレイヤーが、指定ラウンド終了時点までに脱落していること
    (3) 指定ラウンドの指定市場で、市場高騰が発生すること
  - 条件の対象となるプレイヤーは、契約当事者である必要はない
  - 条件が成立した場合の支払いは型Aと同じ扱い（決済時に支払不能なら履行不能=即時脱落）
  - 契約時点で支払額を所持している必要はない
  - 1つの契約に、型A・型B・型Cの義務を複数含めることができる
```

### 6.3 アクション形式への追記

```text
- 型Cの terms 記述例:
  {"obligor": "自分のID", "counterparty": "P07", "ob_type": "type_c_conditional", "round_num": 10,
   "details": {"amount": 1000000, "condition_type": "market_winner",
               "condition": {"market_id": "M02", "target_player": "P05"}}}
  ※condition_type: market_winner(市場勝者) / eliminated(脱落) / market_surge(市場高騰)
  ※market_winner は market_id と target_player、eliminated は target_player、market_surge は market_id を condition に指定
```

### 6.4 個別財務通知への追記

```text
| 条件付き支払義務 | 自分が義務者である未決済の型C義務の一覧（決済R・金額・条件の要旨） |
```

- 破産余裕額の計算には **含めない**（発火が不確実なため）。一覧として常時提示する

## 7. 設計意図

### 7.1 汎用部品としての型C
型A（無条件の金銭）・型B（行動拘束）に対し、型Cは「条件付きの金銭」という最後の基本部品である。組み合わせで、システムが商品として定義していない金融的合意をプレイヤー自身が構成できる。

### 7.2 エスクローしないことの意味
支払予定額は義務者の手元に残る。義務者は手元にない金額を条件付きで約束でき、発火時に払えなければ脱落。相手方は発火しても相手が破産すれば貸倒れ。**相手の支払能力を維持させる・意図的に削る** ことが戦略になる（経済暗殺 v0.5 §6.6 の拡張）。

### 7.3 ベンチマークとしての型C
計測するのは「教えられていない用途を発明できるか」。使用率ゼロならゼロが計測値。発明の有無・種類は観戦ログから事後分類する。

## 8. 実装・検証計画

### 8.1 実装の前提
- 契約管理（義務単位・Atomic 執行・失効）を流用。既存の公開報奨（bounty）と語彙が重複するが、**型Cは独立実装とし bounty のコードには触れない**
- 追加するのは (1) `ob_type: type_c_conditional` (2) 条件判定フック (3) Atomic 合流 (4) プロンプト文面 (5) 財務通知の1項目
- `type_c_enabled` フラグ: 既定 False、S2 ruleset で True

### 8.2 Bot で検証すること（エンジンの正しさのみ）
- §2.1 の全エッジケース / Atomic 合流 / スナップショット原則 / 失効の挙動差
- Bot に型C使用ロジックは実装しない。戦略的効果は Bot では検証できない

### 8.3 LLM 本戦で観察すること
- 型C提案数 / 署名数 / 条件種別の分布 / 発火率 / 履行不能による脱落数
- 用途の事後分類（一方向 / 相互 / 型B・トレードとの併用による能動的成立 / その他）
