ライアーゲーム/カイジ的世界観で複数LLMを対戦させ観戦する企画として始動。限定ジャンケンを下敷きに、公正証書(拘束力ある契約・破れば即死・当事者全員生存中のみ有効=暗殺インセンティブ)、賞金首・怪文書・果たし状、カイジ方式の自己選択借入(ルールを知る前に借入額を選ばせる=開幕からベンチマーク)を発明。この時点で「合理的に嘘をつく能力を測る既存ベンチはほぼない」と気づき、エンタメ兼ベンチマークの二重性が確立。仕様書v0.1。

### サイクル8: Step 3.2調査 — 初の自発的契約提案がエンジンをクラッシュさせた
`--seed 7` の試合が272秒時点で「エラー: 'obligor'」で死亡。調査の結果: LLMが初めてcontract_proposeアクションを自発的に発行したが、プロンプトにtermsの内部構造（obligor/counterparty/ob_type等5フィールド）が一切記載されていなかったため、LLMが独自形式でtermsを構築→エンジンの`term["obligor"]`直接アクセスでKeyError。二重の不幸: (1) `llm_trial.py`のexceptがスタックトレースを握りつぶし、(2) エラーでllm_logger.save()が呼ばれずLLMの生出力（初の契約提案）が回復不能に消失。既存完走4試合を全文検索しても`"type": "contract_propose"`のアクション出力は0件——つまりseed=7が本当に「初」であり、その記録が失われた。修正方針としてP0(トレースバック保全+ログ保全)、P1(terms形式変換+プロンプト例示)、P2(試合を落とさない防御)を提案。テスト73件は非変更。

### サイクル5.1: 実況システムv1 — ずんだもん×めたんAI実況台本生成

trial_C(6社8体戦)の完了済みログから「トレース(リプレイデータ)」を構築し、Haiku 4.5で実況・解説の掛け合い台本を自動生成するシステムを新設した。

**狙い**: 試合ログは数値と構造の羅列で人間には読みにくい。キャラクター付きの掛け合い台本に変換することで、試合の面白さ(裏切り・ブラフ・脅迫)を表面化させ、観戦体験の土台を作る。ずんだもん(公開情報のみ)とめたん(神視点)の情報非対称を制約にすることで、「視聴者が知らない裏側をめたんが暴露する」構造が自然に生まれる。

**実行**: events.jsonl + 全8プレイヤーのllm_calls.jsonl + highlights.jsonlを読み取り専用で解析し、ラウンド単位のパケット(PublicLayer/SecretLayer)に分離。重要な発見として、NEGOTIATION_ACTIONイベントにはメッセージ本文が未記録で、broadcast/DMのテキストはllm_callsのresponse_text内JSONから復元する必要があった。台本生成は1コール/ラウンド方式を採用(掛け合いの自然さ+コスト半減)。秘匿分離はプロンプトで厳格に制約+生成後に自動キーワードチェック。

### サイクル6.0: S2課題1 — Kimi長考問題の根治

**狙い**: trial_CでKimi K2.6がJSON有効率23%・平均レイテンシ99.5s・コスト$5.01(試合全体の45%)・時間占有率72%のボトルネック。根本原因を特定し、JSON率90%以上・レイテンシ60s以下・コスト$1.5/game以下を達成する。

### サイクル7.2: S2シミュレーション結果異常値の調査 — 脱落条件・乱数シード同期 (2026-08-13 13:00 JST)

**発見**:

1. **脱落ゼロは仕様通り**: 生還判定(cash < survival_cash)はR12 Financeのみ。R1-R11の脱落はルートA(破産: Entry Fee不足)とルートB(契約違反)の2経路だが、Botは契約を一切使わず、Entry Fee(10万)も常に支払えるため両方とも発動しない。LLM対戦(trial_B)ではR1,R3で破産が発生しており、途中脱落はLLM特有の現象。

**結論**: 4項目全て「仕様通り」「仕様と実装が一致」。コード修正不要。推奨アクション: (1)比較レポートに「総資産はcashのみ、預託含まず」の注釈追加 (2)スナップショットへの`total_deposits`フィールド追加 (3)途中脱落発生条件でのシミュレーション検討。詳細は `doc/s2_elimination_investigation.md` を参照。

### 2026-08-14 — キャラ立ち絵42枚の白背景透明化

けいすけが用意した6ベンダー×7感情の立ち絵42枚を、ビューアで暗背景に自然に載るよう白背景透明化した。

**狙い**: 単純な「白を消す」は目のハイライトなど内側の白まで消してしまう。輝度・彩度の閾値で背景候補を抽出したうえで、連結成分ラベリングにより**画像の縁に接している成分だけ**を背景と判定する方式（内側の白は残る）を採用。

**実行(1回目)**: `scripts/transparentize_emotions.py` を新規作成。NumPy+Pillow+scipy.ndimage（`uv add scipy`）で実装。輝度閾値240・彩度閾値30で42枚を変換、6×7のコンタクトシートも自動生成。42/42枚成功、1枚のみ極端値（`xai_sadness.png` 15.5%残存）。

**実行(2回目・修正)**: 閾値を108/45に修正し再変換。旧閾値(240/30)と新閾値(108/45)それぞれで`transparentize()`を呼び、各画像の下端20%領域における不透明画素比率を比較する検証を実施——平均43.8%→35.6%（-8.3pp）で足元の影除去が全体傾向として改善したことを確認（個別には髪や服の暗色部が新たに拾われ増加するケースもあり、閾値変更は単純な「悪化/改善」の二値では語れない特性を持つ）。42/42枚再変換成功、極端値は`xai_panic.png`(15.0%)・`xai_sadness.png`(14.5%)の2枚（いずれもキャラ自体の色調が暗く背景との輝度差が小さいことが原因と推定）。

## 2026-08-15 01:30 JST — プレイヤーカードの借入額表示修正（近似計算→正しいデータ源）

### 問題

先行タスクで追加した借入額表示が `debt = cash - free_cash` という近似計算を使用していた。`free_cash = max(0, cash - debt_balance)` のため、`debt_balance > cash` のとき `free_cash = 0` となり `debt = cash`（実際の `debt_balance` より過小評価）になる問題があった。

同一ログ内のINTERESTイベントに正確な `old_debt`（= SNAPSHOT時点の借金残高）が記録されており、近似を使う必要はなかった。

### 修正内容

`viewer/log_parser.py` の `get_game_state()` と `get_round_states()` の両方で:

1. **SNAPSHOT**: `cash` と `cash - free_cash` を取得（`free_cash > 0` のとき正確）
2. **INTEREST イベント**: `old_debt`（= SNAPSHOT時点の正確な借金残高）で上書き
   - `free_cash = 0` のケースを正しく補正する
   - INTEREST は SNAPSHOT の直後に発生するため、`old_debt` がSNAPSHOT時点のdebtに一致する

MANDATORY_REPAY の `new_debt`/`new_cash` は**使用しない**（Finance後の値であり、ラウンド状況パネルのSNAPSHOTベース表示と時点がずれるため）。

### 検証結果（trial_C_20260814_210120 / game01 R6）

| プレイヤー | 現金 | 借金 | 純資産 | 期待値一致 |
|---|---|---|---|---|
| P01 GPT-4.1 Mini | 2,834,088 | 215,457 | 2,618,631 | OK |
| P02 DeepSeek V3 (L) | 2,562,039 | 897,737 | 1,664,302 | OK |
| P05 DeepSeek V3 | 4,044,080 | 1,795,473 | 2,248,607 | OK |

## 2026-08-15 08:49 JST — EventLogger を逐次追記+flush 方式に変更

### 原因

Webビューワーの「ラウンド状況」パネルで、進行中ゲームの過去ラウンド（例: R3進行中にR2選択）で市場の賞金・資産ランキング・提出カード・手札・公正証書が表示されなかった。原因は `EventLogger` がイベントをメモリ上にのみ保持し、`save_jsonl()` がゲーム完了後に1度だけ呼ばれてディスク書き出しする設計のため、進行中は `events.jsonl` がディスク上に存在しなかった。

### 方針A（逐次追記+flush）を採用

`LLMLogger`（`llm/llm_logger.py`）と同パターンで、`EventLogger` に `output_path` パラメータを追加。指定時は `log()` 呼び出しごとに1行ずつ append + flush する。未指定時は従来通りメモリ保持のみ。

### 変更内容

#### 1. `engine/events.py` EventLogger

- コンストラクタに `output_path: str | Path | None = None` を追加
- `log()`: ファイルハンドルが開いていれば即時追記+flush（エラー時はゲーム続行）
- `save_jsonl()`: 逐次書き込み済みで同じパスなら flush のみ（二重書き込み回避）、別パスなら従来通り全書き出し
- `close()`: ファイルハンドルを閉じるメソッド追加

#### 2. `scripts/llm_trial.py`

Phase A/B の `run_trial_game()` と Phase C の `run_trial_game_c()` の2箇所で、EventLogger 生成時に `output_path` を渡すよう変更。既存の `save_jsonl()` 呼び出しはそのまま残す（同一パスなので flush のみ）。

### シミュレーション経路への影響なし確認

以下のスクリプトは全て `EventLogger()` をパスなしで生成しており、逐次書き込みは有効化されない。余分なファイルI/Oは発生しない:
- `scripts/simulate.py`, `scripts/simulate_s2_comparison.py`, `scripts/simulate_surge_change.py`, `scripts/simulate_mandatory_repay.py`, `scripts/compare_schedules.py`, `scripts/mirror_match.py`, `scripts/dry_run.py`

### 2026-08-16 02:07 JST — CoT(A) 実装: reasoning フィールド追加

各LLMエージェントの応答JSONに `reasoning`（推論）フィールドを追加。行動を決める前に状況分析・他者の意図推察・最善手の論理的推論を出力させる仕組み。`enable_cot: bool` フラグで全モデル一律にON/OFF切替可能（デフォルト False、既存挙動完全維持）。

**目的**: 「熟慮するモデルが勝つか」を検証する実験基盤。同一モデルの CoT ON/OFF で因果効果を分離し、可視化する。vendor 固有の native thinking（Gemini等）とは独立した、全モデル共通の「思考軸」。

**実装**:
- `engine/config.py`: `enable_cot: bool = False` フラグ追加
- `llm/prompt_builder.py`: `enable_cot=True` 時、システムプロンプトに reasoning 指示を追加。各フェイズ（loan/negotiation/commit/double_up）のJSON例に `"reasoning": "..."` を条件付き追加
- `llm/response_parser.py`: トップレベルの `reasoning` フィールドを抽出し `strategy["_reasoning"]` に埋め込み。任意フィールド（欠落しても脱落しない）

- `llm/llm_logger.py`: entry に `reasoning` フィールド追加（デフォルト None）

**情報リーク防止（最重要）**: reasoning は**神視点のみ**に記録。`_build_visible_state()` / NEGOTIATION_ACTION イベント / 他プレイヤー向けプロンプトには**一切含まれない**。テスト 3 件で担保。

**コスト面**: reasoning は可視出力トークン（completion_tokens）として課金される。CoT ON で出力トークンが増加するため、試合あたりコストが上昇する。
